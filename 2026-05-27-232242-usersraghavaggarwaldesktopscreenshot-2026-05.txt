  Step 0A — Premise Challenge

  Three things to push back on before any spec lands:

  1. Build vs. buy on the food catalog. This is the biggest scope landmine in
  the ask. "A catalog of basic foods + ability to add foods + click banana
  auto-populate + type 300g greek yogurt and parse" is a real product
  (MyFitnessPal). USDA FoodData Central is free (no API key needed for the basic
   file, key for the API), ~600k items including brand names. Nutritionix has a
  natural-language endpoint that parses "300g greek yogurt" directly — exactly
  the second example. Free tier is 200 req/day. Strong recommendation: do not 
  curate a food catalog. Wrap one of these APIs.

  2. Closed-loop adjustment is the right idea, but anchor it on weight, not 
  WHOOP burn. WHOOP's "total burn" is BMR + activity estimate, and that activity
   estimate is typically off by 10–25%. If we set intake = WHOOP_burn − 500, the
   actual deficit could be 200–800 kcal depending on the day's overestimate. The
   user's instinct is correct: adjust intake based on observed weight change,
  not on predicted deficit. WHOOP burn is a starting point for week 1; the
  closed loop is what makes it converge. We should design week-N intake as:
  intake[N] = intake[N-1] + correction(actual_lbs_lost_last_week − 
  target_lbs_lost_last_week).

  3. Macro targets shouldn't be user-curated; they should be derived. Asking
  "what's your protein/carb/fat goal?" leaks complexity onto the user who
  doesn't know. Body-recomp evidence-based defaults exist: protein 0.8–1.0 g/lb
  bodyweight (preservation during deficit), fat ≥0.3 g/lb (hormonal floor),
  carbs fill the remaining calorie budget. Derive these from current weight +
  intake target; let the user override only if they want to.
